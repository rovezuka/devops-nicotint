# Лабораторная работа 5 — Zero-trust сеть с доказательством

Сеть Kubernetes по умолчанию плоская: любой под может обратиться к любому. Цель работы:
1. доказать, что абстракция Service держит `shop` на плаву, даже когда поды непрерывно умирают и пересоздаются с новыми IP
2. привести `shop` к нулевому доверию («по умолчанию запрещено, открыто только нужное») и доказать это матрицей доступа
3. найти скрытую поломку связности по карте трафика
4. мониторинг сети: метрики, 3 алерта, дашборд

## Окружение и структура

## Часть 2 — Непрерывность при хаосе подов

здесь нужно было открыть `api` наружу через NodePort, запустить скрипт, который будет убивать поды) и еще гонять клиентские запросы, нужно доказать, что клиент не заметил этой резни подов 

### NodePort

сделал `api` доступным снаружи: в `values.yaml` поменял тип Service на `NodePort` с портом `30080`. теперь получается так, что запрос на
порт 30080 любой ноды попадает в `api`

![NodePort: ответ с обеих нод, туннель minikube service](<screenshots/Снимок экрана 2026-10-21 в 23.30.28.png>)

NodePort отличается от LoadBalancer и headless по сути тем, что они все являются типами Service и каждый следующий надстраивается над предыдущим:
- **ClusterIP** это виртуальный адрес внутри кластера
- **NodePort** это ClusterIP + порт на каждой ноде
- **LoadBalancer** это NodePort + внещний балансировщик
- **headless** это `clusterIP: None` - тут нет виртуального адреса, поэтому DNS сразу отдает адреса подов

### Эксперимент с хаосом

подготовил маленький сервис `loadgen`, который 10 раз в секунду обращается к `api` по имени `shop-api.shop.svc` и считает удачные и неудачные запросы

еще подготовил скрипт хаоса (звучит круто очень) `chaos.sh`. он раз в несколько секунд удаляет случайный под `api` или `worker`

отобразил все на панели в дашборде: все удачные запросы, ошибки и сколько разных подов успело смениться

интересно, что первые запуски у меня провалились... опять все из за компа)

### Почему клиент ничего не заметил

когда скрипт удаляет под, происходит так:

1. Kubernetes помечает под на удаление
2. под ждёт 5 секунд и потом аккуратно завершается
3. одновременно под вычёркивается из списка адресов Service, и правила на всех нодах обновляются, в результате чего новые запросы на него больше не идут. пауза в 5 секунд нужна, чтобы это успело произойти до выключения
4. Вместо удалённого создаётся новый под и он при готовности попадает в список

Service — это просто цепочка правил с вероятностями: с шансом 1/3
на первый под, 1/2 из оставшихся — на второй, остальное — на третий:
```
KUBE-SERVICES:  -d 10.97.33.28/32 --dport 80 → KUBE-SVC-…
KUBE-SVC-…:     → 10.0.0.175:8080 (p=1/3) → 10.0.0.250:8080 (p=1/2 от остатка) → 10.0.1.69:8080 (остаток)
```
это список, который просматривается по порядку и переписывается при каждом изменении. на 25 Service это
незаметно, а разница с режимом **IPVS** становится заметной при тысячах сервисов и частых
изменениях

режим kube-proxy у меня это `iptables`. DNS в этой истории делает одно: имя `shop-api.shop.svc` всегда указывает на один и тот же виртуальный адрес Service, сколько бы подов ни менялось и поэтому клиенту не нужно знать адреса подов. список живых подов Service хранит в EndpointSlice, а kube-proxy по нему переписывает правила на нодах

## Часть 3 — Целевая матрица доступа

итак, в этой части нужно было просто спроектировать матрицу: кто к кому должен иметь доступ, а кто не должен

самое опасное здесь это забыть про соединения, которые работают в фоне и не видны, пока не сломаются. поэтому кроме пути заказа записал Prometheus, оператор базы, postgres и DNS в матрицу, чтобы все работало и ничего не ломалось!

| Источник → назначение | Порт | Решение |
|---|---|---|
| loadgen → api | TCP 8080 | ✅ |
| внешний клиент (NodePort) → api | TCP 8080 | ✅ |
| api → postgres, worker → postgres | TCP 5432 | ✅ |
| api ↔ worker | TCP 8080 | ❌ |
| loadgen → postgres | TCP 5432 | ❌ |
| **посторонний под → postgres** | TCP 5432 | ❌ |
| Prometheus (`monitoring`) → api / worker / loadgen | TCP 8080 | ✅ |
| оператор CNPG (`cnpg-system`) → postgres | TCP 8000 | ✅ |
| postgres → Kubernetes API | TCP 443/8443 | ✅ |
| api / worker / loadgen → CoreDNS (`kube-system`) | UDP/TCP 53 | ✅ |
| api / worker → любой другой адрес | любой | ❌ |

## Часть 4 — Zero-trust в чарте

в этой части нужно было реализовать матрицу из предыдущей части в сетевые политики

возьмем `default-deny` для того, чтобы запретить по умолчанию весь трафик к подам в namespace и потом по одному открыть нужные маршруты из матрицы, по меткам подов

| Политика | Что делает |
|---|---|
| `default-deny` | `podSelector: {}`, Ingress + Egress -> все запрещается |
| `dns-egress` | все поды → CoreDNS (`kube-system`, `k8s-app: kube-dns`) : 53 UDP+TCP |
| `api-ingress` | api : 8080 от всех |
| `postgres-ingress` | postgres : 5432 от api, worker; : 8000 от оператора CNPG |
| `metrics-ingress` | api / worker / loadgen : 8080 от Prometheus |
| `app-egress` | api, worker → postgres : 5432 |
| `loadgen-egress` | loadgen → api : 8080 |
| `postgres-egress-api` (**CiliumNetworkPolicy**) | postgres → `toEntities: kube-apiserver` : 443, 8443 |

![NetworkPolicy в namespace shop](<screenshots/Снимок экрана 2026-10-22 в 19.54.54.png>)

на скрине ещё первая версия: доступ postgres к API был обычной NetworkPolicy по IP. она молча не работала, Cilium считает адреса нод особыми, и правило к ним не применялось... поэтому заменил на CiliumNetworkPolicy с `toEntities: kube-apiserver`

## Часть 7 — Мониторинг сети

в конце нужно было собрать сетевые метрики, сделать 3 алерта и показать срабатывания

### Откуда метрики

- **Hubble**: сколько трафика пропущено и сколько отброшено политиками, между кем и кем
- **CoreDNS**: как отвечает DNS
- **Наш клиент**: сколько его запросов не получили ответа

![Prometheus: цель hubble-metrics 2/2 UP](<screenshots/Снимок экрана 2026-10-22 в 21.26.36.png>)

### 3 алерта

| Алерт | Условие |
|---|---|
| `ShopPolicyDrops` (warning, `for: 2m`) | отказы политик, где `shop` с любой стороны, `> 0.1/с` |
| `ShopDNSBlocked` (critical, `for: 1m`) | `rate(hubble_policy_verdicts_total{action="dropped", destination="kube-dns"}) > 0` |
| `ShopClientConnectionFailures` (warning, `for: 2m`) | доля запросов клиента с `code="0"` (нет HTTP-ответа: таймаут, отказ соединения, DNS) `> 5%` |

1 алерт нужен для отображения неверного селектора, порта или когда нет разрешения. по сути этот алерт ловит все поломки, которые закладывали в 6 части

2 алерт был написан, потому что без DNS ляжет весь `shop`. метрики CoreDNS этот сбой не видят, потому что заблокированные запросы до CoreDNS не доходят

3 алерт же нужен чтобы показать сетевой сбой глазами пользователя

## Итоги

- под с точки зрения сети это отдельное пространство. по сути у пода есть свой адрес, они видят друг друга напрямую по IP
- Service может пережить постоянную смену подов. за 10 минут у меня был убит 31 под и 99% запросов клиента прошли. у кластера должно хватать ресурсов
- zero-trust в первую очередь ломает то, о чем забыли... все фоновые соединения занесли в матрицу, но все равно что то может сломаться молча, даже если все поды зеленые
- но эту скрытую поломку можно найти по карте трафика за несколько шагов и починить
- было сделано 3 сетевых алерта, которые потом отразили на дашборде

фух ну вроде все, для меня эти лабы были непростые... но достаточно интересные, спасибо за курс!!!
