## Часть 2 — namespaces

![linux meme](lab-1-docker/linux.jpg)


### Шаг 2.1. Запуск через `unshare`
сначала выполнил sudo `sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, чтобы снять ограничение user namespace заложенное с `ubuntu 24.04`

поместил с помощью unshare процесс в свои `namespace`, обязательно должен быть флаг `--user` с `user ns`, потому что от его

имени будут создаваться следующие namespace для процесса и нам не нужен sudo для выполнения команды

посмотрел флаги через `man unshare` и вывел следующее флаги для `ns unshare --pid --mount --net --uts --ipc --user`

![hostname proccess](lab-1-docker/hostname внутри процесса.png)

и флаги вспомогательные: `--fork --mount-proc --map-root-user`

вся команда `unshare --pid --mount --net --uts --ipc --user --fork --mount-proc --map-root-user bash`

`bash` в конце чтобы запустить оболочку для выполнения команд внутри процесса

### Шаг 5.3. Сравнение

основные различия, которые я заметил: 
- в скрипте нет корневой файловой системы, он видит всю ВМ, а в контейнере докера своя из слоев образа
- скрипт в отличии от докера не создает сетевой интерфейс `eth0`
- у скрипта сброшены `capabilites`, а у докер есть дефолтные 14 действий, которые процесс (контейнер) может сделать
- также по дефолту есть `seccomp` профиль который накладывает 60 ограничений, но если мы засунем свой профиль, то перезапишем все ограничения и снизим защиту

CPU в ядрах, это `rate()` от счётчика

один график CPU ничего не говорит о страданиях сервиса, потому что голый счетчик всегда увеличивается и мы не можем сделать выводы по этому показателю

нужно смотреть на троттлинг, он напрямую влияет на `latency` сервиса 

### алерты

делаем алерты:

- троттлинг > 20 % периодов за 5 минут, значит что приложение регулярно зависает и увеличивается latency 

- память > 80 % лимита за 5 минут, значит что скоро может быть оом киллед

- рестарты контейнера >3 за 15 минут, значит что контейнер регулярно останавливается из-за oom_killed
