# Лабораторная работа 8

Цель работы - придумать реальный devops-кейс и собрать его как воркфлоу в n8n: с ИИ-агентом, MCP-серверами и мониторингом. Мы выбрали кейс автоматического ревью пулл-реквестов на случайно закоммиченные секреты.

## Часть 1. Кейс

Контекст мы придумали такой. Небольшая команда поддерживает внутренний сервис платежей `payments-api`. Код ревьюят разработчики по очереди, и периодически в коммиты попадают токены и пароли: кто-то скопировал строку из локального `.env`, кто-то вставил живой токен в пример для документации. Отзывать токен после того, как он уехал в репозиторий, дорого и неприятно, поэтому такие вещи хочется ловить до мержа.

Руками просматривать каждый дифф не хочется: рутина, её откладывают на потом, и глаз со временем замыливается. Поэтому мы автоматизировали процесс.

Что делает автоматизация от начала до конца:

1. разработчик открывает PR или пушит новые коммиты в существующий;
2. GitHub присылает вебхук, n8n его принимает;
3. детерминированный сканер (обычный код, без ИИ) проверяет добавленные строки диффа: приватные ключи, префиксы токенов вроде `sk-live-`, присваивания с именами вида `password`, `token`;
4. ИИ-агент читает политику классификации и белый список, и классифицирует каждую находку: `block`, `warn` или `false_positive`;
5. агент записывает отчёт в файл и оставляет комментарий в PR с вердиктом.

Важно, что процесс полностью автоматический: GitHub сам присылает вебхук и при открытии PR, и при новых коммитах в него, агент сам всё проверяет и сам постит комментарий с вердиктом обратно в PR. Единственное действие человека - открыть PR, что он и так делает.

Кому это помогает: разработчикам (не надо вручную выискивать секреты в диффах) и бизнесу (снижает риск утечки секретов).

## Часть 2. Реализация

### Архитектура

```text
GitHub PR webhook
        ↓
ngrok (туннель)
        ↓
n8n (Docker Compose)
        ↓
github-mcp ←→ GitHub API
filesystem MCP → /files/policy, /files/reports
        ↓
ИИ-агент (модель через API)
        ↓
отчёт + комментарий в PR
        ↓
экспортер → Prometheus/Grafana (стек из лабы 2)
```

### MCP-серверы

По заданию нужно минимум два MCP-сервера, и у нас они подключаются по-разному.

GitHub MCP - официальный сервер от GitHub. Он умеет HTTP-транспорт, поэтому живет отдельным контейнером рядом с n8n, как сайдкар. n8n ходит на него по внутренней сети Docker Compose.

Filesystem MCP работает только через stdio, то есть его должен запустить родительский процесс. Из коробки n8n stdio-серверы запускать не умеет, поэтому мы поставили community-пакет `n8n-nodes-mcp`: его нода умеет порождать такие процессы внутри контейнера n8n. Серверу мы передали ровно два каталога, `/files/policy` (политики, только чтение) и `/files/reports` (отчёты). Больше ему ничего не нужно.

### Toolkit агента

| Тул | Откуда | Что делает | Что принимает |
| --- | --- | --- | --- |
| `pull_request_read` | GitHub MCP | забирает файлы и дифф PR | owner, repo, pullNumber, method |
| `scan_diff` | Code Tool | детерминированный сканер секретов | массив файлов с добавленными строками |
| `read_file` | filesystem MCP | читает политику и белый список | путь |
| `write_file` | filesystem MCP | пишет отчёт | путь и содержимое |
| `pull_request_review_write` | GitHub MCP | оставляет комментарий в PR | owner, repo, pullNumber, event, body |

`scan_diff` - это наша собственная Code Tool нода. Внутри обычный сканер на регулярках: приватные ключи, `ghp_`, `AKIA`, `sk-live-`, присваивания с "секретными" именами переменных. Сканер возвращает находки с масками значений (вида `sk-l***ret`) и severity.

### Скилл агента

Скилл лежит в `policy/agent-skill.md` и вставляется агенту в системный промпт. Порядок действий: получить дифф, прогнать сканер, прочитать политику, классифицировать находки, записать отчёт, оставить комментарий, вернуть вердикт.

Самое важное в скилле - правила безопасности:

- никогда не выводить полное значение секрета, только маски от сканера;
- асимметрия доверия: агент может смягчить `warn` до `false_positive` (например, если значение читается из окружения через `os.getenv`, секрета в диффе нет), но не может понизить `block`. Если сканер пометил находку как `block`, итоговый вердикт `block`, без исключений;
- белый список применяется только по точному совпадению значения, не по подстроке.

Асимметрия - это защита от фантазий модели: критичные решения остаются за детерминированным слоем, агент только добавляет контекст.

### Воркфлоу

К финальному виду мы шли в несколько итераций.

Первая версия была чисто детерминированной, без всякого агента:

```text
Webhook → Scan Secrets → Read Allowlist → Apply Allowlist → Respond
```

Code-нода сканировала добавленные строки диффа на регулярки, следующая читала с диска белый список и применяла его к находкам. Всю цепочку мы гоняли curl-ом с моковым payload: сканер находил "секрет", allowlist отсекал плейсхолдеры, полное значение наружу не утекало. По сути мы проверили всю детерминированную логику до того, как подключили модель.

Но по заданию работу должен делать ИИ-агент со своим тулкитом, поэтому вторая итерация была архитектурной: сканер мы не выкинули, а разжаловали из самой цепочки в тул агента. Детерминированный конвейер свернулся в инструменты, оркестрацию вызовов взял на себя агент, порядок действий зафиксировал скилл.

Третья итерация - сборка агента по частям, с прогоном curl-ом на каждом шаге. Сначала каркас: Webhook → Extract PR → AI Agent с одной чат-моделью и без тулов. Потом тулы по одному: GitHub MCP, scan_diff как Code Tool, filesystem MCP.

Финальный вид:

```text
Webhook → Extract PR → IF ──(ping)──→ Respond (ok)
                          └─(PR)──→ AI Agent → Respond (verdict)
```

Extract PR - обычная Code нода без ИИ: достает из вебхука owner, repo, номер PR и head SHA.

### Выбор модели

В качестве провайдера использовали Openrouter.
Сначала попробовали использовать minimax-m3.1-flash-free, но столкнулись с интересной проблемой. Агент без единого подключенного тула "выполнил" весь воркфлоу: прислал дифф, просканировал, записал отчёт. Проблема в том, что всё это модель выдумала: файлы в "диффе" не совпадали с реальными, SHA был вида `a1b2c3d4...`, а отчёта на диске не оказалось. Для security-инструмента уверенная выдумка хуже падения: ревьюер отчитался, и все думают, что проверка была.

В итоге поменяли на дешевый deepseek-v4.1-flash-1017, и вот он уже не галлюцинировал и нормально поддерживал вызовы тулов через API.

### ngrok и асинхронный ответ

Для реального вебхука GitHub нужен публичный URL, локальный n8n снаружи не виден. Мы подняли туннель:

```bash
ngrok http 5678
```

и зарегистрировали вебхук в настройках демо-репозитория (события Pull requests).

Тут вылезли две проблемы.

Первая: при регистрации вебхука GitHub присылает ping-событие, а в его payload нет ни номера PR, ни SHA. Из-за этого валидация в Extract PR падала. Добавили фильтр по заголовку `x-github-event`: на ping отвечаем 200 и выходим, на события PR запускаем ревью (видно на скрине выше - блок if).

Вторая: ngrok рвал соединение секунд через десять (ошибка 3004), GitHub получал таймаут и помечал доставку как проваленную, хотя по факту воркфлоу запускался. Причина в том, что агент с несколькими вызовами тулов и запросами к модели в десять секунд, очевидно, не укладывается. Развернули схему в асинхронную: Respond to Webhook отвечает GitHub сразу после приема вебхука, а агент работает в фоне. Это ровно то, как живут настоящие CI-системы: вебхук подтверждает прием, результат прилетает позже комментарием в PR.

На скрине есть пометки "redelivery" - переотправлять готовые события было проще для тестирования чем каждый раз делать pr/коммит. Но первые доставки были вызваны по-настоящему а не синтетически, так что все честно. Synchronize - событие об обновлении pr (в нашем случае добавление коммита).

## Часть 4. Мониторинг

### Экспортер

n8n из коробки не отдает метрики в формате Prometheus, так что по заданию мы написали отдельный экспортер: маленький Python-скрипт (requests + prometheus_client), который раз в 30 секунд опрашивает n8n API и отдает `/metrics` на порту 9200.

Метрики:

- `n8n_webhook_up` - жив ли эндпоинт вебхука;
- `n8n_workflow_runs_total` - счетчик запусков воркфлоу по статусам;
- `n8n_review_duration_seconds` - длительность последнего успешного ревью;
- `n8n_exporter_api_errors_total` - ошибки опроса API, то есть здоровье самого экспортера.

Сетевая часть - та же граница, что была во второй лабе: Prometheus внутри Minikube не видит localhost хоста. Экспортер слушает на `0.0.0.0`, а Prometheus скрейпит его по адресу `192.168.49.1:9200` (gateway docker-сети Minikube). Стек мониторинга мы не поднимали заново, а переиспользовали Prometheus и Grafana из второй лабы: добавили additional scrape config при helm upgrade.

### Алерты

По заданию нужно было выбрать три метрики для алертов и обосновать выбор. Мы выбрали три разных режима отказа.

1. `SecretReviewerWebhookDown`: `n8n_webhook_up == 0` в течение 2 минут. Это триггер всей системы: если вебхук мертв, ревью вообще не запускается, и никто этого не заметит, пока не всплывет утечка. Самая дорогая тишина, поэтому severity critical.

2. `SecretReviewerWorkflowErrors`: ошибки воркфлоу за 15 минут. PR, вызвавший ошибку, остался без ревью, при этом GitHub уже получил свой 200 (мы отвечаем мгновенно), то есть асинхронность скрывает сбой. Без алерта владелец PR не узнает, что его никто не проверил.

3. `SecretReviewerSlowReview`: `n8n_review_duration_seconds > 120` в течение 10 минут. Ранняя деградация: если модель или MCP-серверы тормозят, это видно до того, как что-то упадет окончательно.

Общая логика простая: сломанный ревьюер выглядит как работающий, поэтому каждый алерт закрывает свой режим отказа (мертв, падает, тормозит).

## Итог

Собрали полный цикл: реальный вебхук GitHub через ngrok, ИИ-агент с пятью тулами и двумя MCP-серверами, детерминированный сканер как источник истины для критичных находок, отчёты и комментарии в PR, и мониторинг всей этой системы поверх стека из второй лабы.

Главное - процесс полностью без кнопок: разработчик просто открывает PR, дальше система сама получает событие, сама проверяет дифф, сама пишет отчёт и сама оставляет комментарий с вердиктом прямо в тред PR. На вид прямо как в какой-нибудь компании, что довольно круто.
